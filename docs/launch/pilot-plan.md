# План пилота на первых каналах

**Требует действий человека:** отбор участников, договорённости с ними, решения по итогам. Значения с меткой ПРЕДПОЛОЖЕНИЕ П-6 придуманы и подлежат замене.

## Рамки

| | Значение |
|---|---|
| Сроки | 4 недели, 16.11.2026 – 13.12.2026 (ПРЕДПОЛОЖЕНИЕ П-6) |
| Каналы | 5–10 каналов MAX от 1 000 до 10 000 подписчиков — ниже порога реестра РКН (`RKN_SUBSCRIBERS_THRESHOLD`, 06 §6.3) |
| Рекламодатели | 3–5, знакомые владельцу площадки, с безналичной оплатой по счёту |
| Объём | до 30 размещений |
| Комиссия | 15 % (`PLATFORM_FEE_RATE_BP=1500`) |
| Дежурство | ИП, 10:00–19:00 МСК; вне этого времени — по оповещению (ПРЕДПОЛОЖЕНИЕ П-9) |

## Цели и критерии успеха

| Цель | Как меряем | Критерий |
|---|---|---|
| Размещения проходят без ручного вмешательства | доля размещений, дошедших от оформления до приёмки без действий администратора (кроме модерации) | ≥ 90 % |
| Публикации маркированы | у каждой публикации есть erid; нарушений I-01 нет | 100 % |
| Контроль работает | нарушения (досрочное удаление, правка, «часы в топе») находятся системой; споры решены в срок `DISPUTE_DEADLINE` | все нарушения найдены; споры ≤ 72 ч |
| Деньги сходятся | задание `check_ledger_balance` без расхождений; каждое поступление сопоставлено; выплаты прошли | 0 расхождений; выплаты ≤ 72 ч после приёмки (T-12) |
| Дежурный успевает | время от оповещения до реакции в рабочие часы | ≤ 30 мин |
| Работа без простоя | выпуски за время пилота без ошибок 5xx у пользователей; `backup` здоров; еженедельная проверка восстановления проходит | 0 инцидентов простоя по вине выпуска |

## Отбор участников

- Каналы: тематика без ограничений рекламы 06 §7 (не алкоголь, не финансы, не медицина — на пилоте), владелец — самозанятый или ИП, готов пройти онбординг Рокет Ворк, добавить бота с правами публикации и удаления.
- Рекламодатели: ИП или юрлица, готовы платить по счёту, понимают, что идёт пилот.
- Каждому участнику — короткое объяснение: что делает бот, как принимаются и оспариваются размещения, куда писать.

## Ежедневный порядок дежурного

1. **Утро (10:00).** Оповещения за ночь (почта, чат). `docker compose ps`: все контейнеры `healthy`. Журнал `backup`: ночные копии `dump_done`, `base_done`, `objects_done` без ошибок (`dc logs --since 24h backup | jq -c 'select(.level != "debug")'`).
2. **Деньги.** Выписка банка за прошлый день: `maxim admin money statement import`; несопоставленные поступления — `bank-tx list`, ручное сопоставление `bank-tx match`. Сверка `admin money reconcile`.
3. **Маркировка.** Экран ошибок ОРД (S-20, `GET /api/v1/admin/ord/errors`) или `maxim admin ord errors`: объекты ОРД в ошибке, включая строки статистики и акты; исправимые — повтор с основанием (`POST …/retry`, `admin ord retry`); зависшие erid (T-11) — разбор.
4. **Подтверждения.** Запросы второго подтверждения денежных операций (`GET /api/v1/admin/approvals`, счётчик `approvals_pending`): решает другой `senior` до истечения `ADMIN_APPROVAL_TTL` (72 ч).
5. **Размещения.** Зависшие объекты из оповещений: публикации `removal_overdue`, размещения в `scheduled` без публикации, споры с истекающим сроком.
6. **Модерация.** Посты и каналы в очереди: пост — 24 ч, срочный — 1 ч (T-07).
7. **Вечер (19:00).** Итог дня в журнал дежурного: размещения, споры, ручные действия, инциденты.
8. **Воскресенье.** Результат `restore_check_result` в журнале `backup`.

Операции администратора — через API администратора (кабинет `adm/*`; доступ только с адресов `EDGE_ADMIN_ALLOW`) или командами `maxim admin …` на сервере через `docker compose run --rm migrate admin …` ([deploy/app/README.md](../../deploy/app/README.md#api-администратора-и-отчётность-орд)).

### Ежемесячная отчётность ОРД (S-31, 05 §3.7)

1. **1-е число.** Задание `ord_monthly_report` в 00:05 МСК делает снимок просмотров живых публикаций и формирует статистику и акты прошлого месяца (`ORD_REPORT_AUTO_SEND=false` — не отправляет).
2. **1–5-е число.** Дежурный (`senior`) открывает отчёт (`GET /api/v1/admin/ord/reports/<ГГГГ-ММ>` или `maxim admin ord report show --period <ГГГГ-ММ>`), сверяет число строк и суммы с размещениями месяца и отправляет: `POST …/send` с основанием или `admin ord report send --period … --reason … --email <senior>`. Состояние `sent` — всё подтверждено ОРД.
3. **Ошибки.** Строки и акты в `error` — на экране ошибок ОРД; после исправления — повтор или повторная отправка отчёта. Решён спор по прошлому месяцу — `POST …/rebuild` (или `admin ord report build`), затем отправка: изменившиеся записи уходят заново (в течение 30 дней, 05 §3.7).
4. **До 20-го.** С `ORD_REPORT_ERROR_DAY` (20-е) неотправленный отчёт — оповещение `ord_report_overdue:<период>` раз в сутки; срок сдачи в ответе отчёта (`due_date`, 30-е число, проверить с юристом).

## Остановка и откат

| Ситуация | Действие |
|---|---|
| Публикация без erid или в чужом канале | немедленно: остановить ячейки `worker` (`dc stop worker-a worker-b`) — публикации и снятия прекращаются; разбор; при необходимости — снятие поста вручную |
| Расхождение журнала проводок | остановить приём оплат (не выставлять счета), разбор по `check_ledger_balance`; выплаты не делать до сходимости |
| Ошибка после выпуска | `release.sh --rollback` (Actions → release, `rollback`) |
| Потеря базы | восстановление по [deploy/app/README.md](../../deploy/app/README.md#резервные-копии); участникам — сообщение о простое |
| Претензии участников к условиям | пауза новых заказов (не принимать размещения), правка правил, новая версия документа |

Критерий остановки пилота целиком: повторяющаяся публикация без маркировки, необъяснённое расхождение денег или утечка ПДн ([personal-data.md](personal-data.md#утечка)).
