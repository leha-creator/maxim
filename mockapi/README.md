# Тестовый сервер API кабинетов

Заглушка HTTP API кабинетов рекламодателя и блогера по спецификации [`../api/openapi.yaml`](../api/openapi.yaml). Нужна, чтобы руками пройти сценарии в Swagger UI и посмотреть, как устроено API.

Чем сервер **не является**:

- **Не каркас продукта.** Структура настоящего бэкенда выбирается на этапе «Каркас бэкенда и аккаунты» (`docs/07-non-functional.md` §1).
- **Данные выдуманные.** Названия, ИНН, ссылки, erid, чеки ненастоящие; почты — в домене `example.test`.
- **Всё хранится в памяти.** Изменения живут до перезапуска или до `POST /api/v1/_mock/reset`.
- **Внешних систем нет.** MAX, Яндекс ОРД, Рокет Ворк, банк и почта не вызываются. Их роль играют операции `_mock`.

## Запуск

Нужен Go 1.25 или новее (`winget install GoLang.Go`).

```sh
cd mockapi
go run ./cmd/mockapi
```

Swagger UI открывается на <http://localhost:8080/docs>, спецификация отдаётся по адресу <http://localhost:8080/openapi.json>.

Версия сборки задаётся через `-ldflags "-X main.version=<sha>"` и пишется в строку журнала `server started`; по умолчанию — `dev`.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `MOCKAPI_ADDR` | `:8080` | Адрес сервера |
| `LOG_LEVEL` | `debug` | `debug`, `info`, `warn`, `error` |
| `MOCKAPI_COOKIE_SECURE` | `false` | `true` — cookie сессии с признаком `Secure`; включается на стенде по HTTPS |

Журнал пишется в JSON, по строке на запись, в stdout. Пример:

```json
{"time":"2026-10-15T10:32:37Z","level":"INFO","msg":"placement transition applied","component":"mockapi","module":"store","request_id":"01a13f1e-…","op":"Placement.Transition","placement_id":"…","transition":"P-03","from":"awaiting_blogger","to":"awaiting_schedule","actor_type":"blogger"}
```

Каждый ответ содержит заголовок `X-Request-Id`. По этому значению запрос находится в журнале.

## Вход

Код входа всегда `000000`. Письма не отправляются.

| Почта | Кто |
|---|---|
| `adv@example.test` | Рекламодатель: ООО, баланс 1 000 000 ₽, корзина из двух каналов, три кампании |
| `blg@example.test` | Блогер: ИП, шесть каналов, исполнитель Рокет Ворк активен, запросы в разных состояниях |
| `adm@example.test` | Администратор `senior` без организации: модерация каналов (`/admin/channels`), в очереди — канал 113 с номером РКН на сверке |

Любая другая почта создаёт нового пользователя без организации; реквизиты заполняются через `POST /organizations`.

Как войти в Swagger UI:

1. Откройте `POST /auth/login`.
2. Отправьте `{"email": "adv@example.test", "code": "000000"}`.
3. Браузер сохранит cookie `session`, и дальше запросы пойдут от имени этого пользователя.

Чтобы сменить пользователя, войдите под другой почтой.

## Сквозной сценарий

Идентификаторы начальных данных фиксированы: `0190a000-0000-7000-8000-<номер из 12 цифр>`.

**Рекламодатель** (`adv@example.test`):

1. `GET /cart` — две позиции из начальных данных.
2. `PUT /campaigns/{id}/post` для кампании `…000000000601` — пример тела уже заполнен в Swagger UI.
3. `POST /campaigns/{id}/post/preview` — текст в формате MAX и пример строки маркировки.
4. `POST /campaigns/{id}/checkout` — заказ создан, деньги удержаны (`GET /balance`).

**Модерация и маркировка**, без входа:

5. `POST /_mock/orders/{id}/approve-post` с идентификатором нового заказа. Пост одобрен, получен erid, размещения перешли в `awaiting_blogger`.

**Блогер** (`blg@example.test`):

6. `GET /blogger/placements?status=awaiting_blogger` — найдите размещение на канале `…000000000101`.
7. `POST /blogger/placements/{id}/accept`, затем `POST …/schedule` с телом `{"mode": "at", "publish_at": "<время внутри периода кампании, не раньше чем через час>"}`.

**Система**, без входа:

8. `POST /_mock/placements/{id}/advance` с `{"transition": "P-08"}` — пост опубликован; затем с `{"transition": "P-10"}` — снят. Часы сервера сдвигаются на время публикации и снятия.

**Рекламодатель:**

9. `POST /placements/{id}/accept` — размещение принято. Повторный вызов вернёт `409 invalid_transition`.

**Система:**

10. `POST /_mock/placements/{id}/advance` с `{"transition": "P-16"}` — выплата прошла; блогер видит её в `GET /blogger/payouts`.

Таймеры проверяются сдвигом часов: `POST /_mock/clock` с `{"hours": 25}`. Сработают истёкшие таймеры: T-01 (блогер не принял), T-13 (не запланировал), T-05 (автоприёмка). В ответе перечислены выполненные переходы. `POST /_mock/invoices/{id}/pay` зачисляет счёт на баланс.

Тот же сценарий выполняет тест `TestScenarioFullCycle`.

## Устройство

| Каталог | Что внутри |
|---|---|
| `internal/api` | Код, сгенерированный из спецификации (`oapi-codegen`): модели, маршруты, strict-интерфейс сервера, встроенная спецификация |
| `internal/server` | Промежуточные слои: сквозной идентификатор, журнал, восстановление после паники, сессия, проверка запросов по спецификации. Swagger UI |
| `internal/handlers` | Реализация операций, по файлу на группу |
| `internal/store` | Хранилище в памяти, таблица переходов размещения (03 §4), таймеры, деньги, сериализация поста |
| `internal/seed` | Начальные данные |
| `internal/clock` | Подменяемые часы |

После правки `api/openapi.yaml` нужно перегенерировать код:

```sh
go generate ./...
```

Сгенерированный файл `internal/api/api.gen.go` хранится в репозитории.

## Тесты

```sh
go test ./...
```

| Тест | Что проверяет |
|---|---|
| `TestSpecIsValid` | Файл спецификации проходит проверку `kin-openapi`; встроенная копия не устарела |
| `TestEveryOperation` | Каждую операцию спецификации на свежих начальных данных: ответ успешный и совпадает со схемой. Падает, если у операции нет тестового случая |
| `TestValidatorRejectsMismatch` | Что сама проверка ответов отклоняет неверное тело и необъявленный статус |
| `TestScenarioFullCycle`, `TestTimerFiresOnClockShift`, `TestAccessIsolation` | Сквозной сценарий, таймер T-01, изоляция кабинетов |
| `gaps_test.go` | Ответы, на которые опирается фронтенд: `details.reason` в `409` и `422`, `inn_taken`, `post_problems`, `total`, суммы строк отчёта, спор, `read-all`, модерация каналов |

## Что упрощено или не сделано

- **Раздел администратора** — только модерация каналов (`admin-channels`). Модерация поста заменена на `_mock/orders/{id}/approve-post` и `reject-post`. Канал после правки блогером проходит автоматическую модерацию сразу; в очереди остаются каналы из начальных данных. Споры остаются в `disputed`.
- **Защита от подделки запросов.** Заголовок `X-CSRF-Token` описан, но не проверяется. Признак `Secure` у cookie ставится только при `MOCKAPI_COOKIE_SECURE=true`: локально сервер работает по http.
- **Ограничение частоты запросов** не реализовано.
- **Файлы** не сохраняются. Проверяются только тип по содержимому и размер. Картинки в ответах — заглушки с `placehold.co`.
- **Сериализатор поста** использует условные HTML-теги. Точные теги MAX — задача продукта (Q-06). UTM-метки к ссылкам не добавляются.
- **Деньги** ведутся как движения баланса рекламодателя, без плана счетов 06 §2. Пропорционального возврата нет.
- **Не реализовано:** правило «до конца окна дат меньше часа» (03 §4, особые правила) и таймеры T-02 … T-12. Публикация и снятие выполняются только через `_mock/…/advance`.
- **Webhook** MAX и Рокет Ворк принимаются и игнорируются.
